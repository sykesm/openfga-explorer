Context, contextual tuples & walk options

Request context: values for the parameters of conditions, as JSON (Check's context), for example the current time or the caller's IP address. A condition whose parameters are missing shows as “missing parameters” in the result.

Contextual tuples: tuples that count for this check only, as if they were written (OpenFGA's contextual tuples). Nothing is stored. Use them to ask “what if”: would this user have access if they joined that group? They are marked “(contextual)” in the text trace.

Evaluation order: how the walk treats the branches of a rule like viewer or editor. Shortest explanation (default): the server's Check says which branches hold, the walk follows one that decides, and the others are shown as “not evaluated” with the server's verdict. Fewest calls. Model order: branches are tried in the order the model lists them, stopping at the first that decides, as a step-by-step evaluator would. Can use many calls on deep group trees. Every path: every branch is evaluated, so every way the user gets access is shown. Uses the most calls.

Verify with server Check: whether the steps the walk decides are confirmed with OpenFGA's own Check, so any difference between the walk and the server is flagged. Every relation (default): every relation in the walk is checked. Root + undecided: only the overall answer and the steps the walk could not decide. Off: nothing is checked; the result is the walk's alone. Verification calls do not count against the call budget.

Consistency: sent to OpenFGA with every read and Check. Minimize latency (default) lets OpenFGA answer from its cache, so very recent writes may not show yet. Higher consistency reads the latest data, skipping the cache; slower.

Call budget: the most OpenFGA API calls the walk may make (verification calls are separate). If it runs out, the walk stops, the parts it did not reach are “undecided”, and the result offers to run again with a bigger budget.

Edges per step: how many tuples behind one edge (the members of [group#member], the parents of viewer from parent) the walk follows one by one. When there are more, it asks OpenFGA's ListObjects which of them the user belongs to (a “probe”) and follows only those.

Probe lookups: how many of the groups or parents a probe finds are looked up in one step. If the user belongs to more, the rest are not looked up and the step can be left undecided; the step's details say how many were looked up.
